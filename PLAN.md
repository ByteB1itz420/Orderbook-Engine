# Orderbook-Engine: build plan

**Goal:** A C++20 limit order book, deterministic market-data replay, correctness suite, reproducible benchmarks, and interview-ready demo. Build for quant-developer and strong software-engineering interviews. This is an execution plan, not a claim that every feature is already complete or that the engine models Nasdaq's actual matching rules.

**Starting point:** The previously prepared M1 bundle reportedly includes CMake, CI, a matcher, a LOBSTER parser/replay path, 26 tests, sanitizer coverage, and a beginner walkthrough. Audit its actual source and run its tests before marking any item below done. Work through the code with Ayush; he should be able to explain each retained component in plain language. Keep scope to one instrument and one matching thread, with a single reproducible historical sample. Do not add distributed services, live exchange connectivity, a trading strategy, or GPU optimization to the core project.

## 1. Define the matching contract

- [ ] Write a short `docs/semantics.md` with integer tick prices, integer share quantities, order IDs, buy/sell sides, accepted and rejected input, and deterministic event ordering. Work through a small event sequence by hand before implementing or refactoring it.
- [ ] Implement/verify limit orders, market orders, marketable limits, partial fills, resting remainder, cancellation by ID, and modification/replacement. State explicitly whether a market order's unfilled portion expires, and whether a limit order's remainder rests. Execution price is the resting order's limit price in this simulator.
- [ ] Enforce highest bid/lowest ask, then FIFO within each price level. Document modify priority: a same-price quantity decrease can retain place; price change or size increase loses its old place through cancel-and-readd. Decide and test zero/invalid quantities, off-tick prices, unknown/duplicate IDs, insufficient pool capacity, and integer overflow.
- [ ] Emit ordered trade records (maker ID, taker ID, price, size, sequence) and order acknowledgments/rejections. Match a crossing incoming order repeatedly until its quantity is exhausted or the opposite book no longer crosses. Keep book state and emitted trades in one deterministic transition.
- [ ] Treat IOC, self-trade prevention, hidden liquidity, auctions, and exchange-specific behavior as explicitly labeled optional extensions or documented existing behavior, not a claim of Nasdaq parity. Fix the core contract before adding order types.

### Data structures and the interview answer

- [ ] Maintain ordered bid and ask price levels with direct best-price access. A tree is a clear baseline: insertion/removal of a level costs logarithmic time; matching at the cached best is direct. Consider a bounded dense price ladder only if measured traces justify its range and memory cost.
- [ ] Store orders at each level in an intrusive doubly linked FIFO list. With an order ID mapped to a stable node, cancel can unlink in constant time and matching can consume the head without scanning the queue. Explain the extra pointers and cache tradeoff.
- [ ] Use an ID-to-node lookup. Start with `std::unordered_map` as a baseline; test an open-addressing/flat hash map only if its memory/locality benefit is measured and its invalidation/rehash rules are understood. Reserve capacity. Avoid undocumented dependency complexity for a small gain.
- [ ] Give nodes stable addresses with a preallocated pool/free list and an explicit capacity policy. Reserve trade-output storage or use a bounded sink. Instrument allocations to establish that the *bounded, warmed matching path* has no dynamic allocations. CSV parsing, initialization, output, overflow handling, and the web demo are not part of that claim. Avoid logging, file I/O, formatting, and syscalls in the measured hot path.
- [ ] Record the baseline and any optimized variant, with the same correctness tests. Retain simpler code if optimization gains are small, noisy, or harmful to tail latency.

## 2. Historical replay and synthetic order flow

- [ ] Use the free LOBSTER sample paired **message + orderbook CSV** for one ticker/day, initially 10 displayed levels. It is small and has row-aligned snapshots to check reconstruction. Record exact file names, source URL, session/window, hash, and any sample-use restriction. Do not silently publish raw sample data in a public repo or website.
- [ ] Parse timestamps, event types, IDs, sizes, integer prices, and side without floating-point price arithmetic. Consume events in file order; retain their original sequence and report malformed/unsupported rows. Establish the starting-state/window rule before making a depth-comparison claim.
- [ ] Keep two pipelines separate: (a) **historical reconstruction**, applying observed add, partial cancel, delete, and visible-execution deltas to resting orders; (b) **matching simulation**, supplying seeded synthetic incoming market/limit/cancel/modify commands to the engine and generating its own fills. An historical execution is an observed reduction of a resting order, not a fresh incoming order that should be matched a second time. An outbound ITCH feed is not an order-entry feed.
- [ ] Handle LOBSTER hidden executions, cross/auction events, halts, dummy zero-volume levels, changes outside displayed depth, and missing prior state with documented skip/unsupported rules and counters. Compare supported reconstructed displayed depth to supplied snapshots and publish match counts, mismatch examples, and reasons, not a blanket “exchange-accurate” claim. The single visible venue cannot reveal all hidden liquidity, cross-venue queue position, or true market impact.
- [ ] Keep a deterministic synthetic trace generator for corner cases and the public demo. Defer native Nasdaq ITCH 5.0 parsing to a stretch goal: its official binary schema is educational, but sample files are multi-gigabyte and parsing administrative, symbol, and session messages materially enlarges scope.

## 3. Correctness gate

- [ ] Write targeted tests for best-price precedence, FIFO at equal price, multi-level sweeps, partial fills, modify priority, duplicate/unknown IDs, empty-side market orders, exact exhaustion, invalid size/price, capacity exhaustion, and any retained IOC/self-trade rules.
- [ ] In a debug verification mode, check after each event: bid/ask order, noncrossed resting book after matching, list links and ID-map consistency, unique live IDs, strictly positive resting quantities, cached best pointers, and each level's aggregate quantity equal to its nodes' sum. For a match, assert incoming filled plus remaining/expired quantity equals original input and each execution reduces corresponding maker quantity by its size. Use wider arithmetic or checked sums.
- [ ] Compare thousands of seeded, short random traces against a deliberately simple independent reference matcher. Preserve the seed and reduce a failing trace to the smallest sequence. Run ASan/UBSan in CI; add a focused fuzz/property target for the transition parser or matcher only if the basic random differential suite is in place.
- [ ] Save small golden traces and expected trades/books. Validate supported LOBSTER rows against the paired depth file, reporting exact denominators, skip counts, mismatch categories, and any warm-up/state caveat. Never call a test suite proof of all exchange behavior.

## 4. Benchmarks and performance report

- [ ] Freeze benchmark inputs and method before looking at optimized results: source hashes/seeds, event mix, book size/depth, number of events, warm-up, repeated runs, compiler/version/flags, build mode, CPU model, memory, OS, CPU-affinity/power/frequency conditions, and whether input is cached in memory. Keep a simple baseline for comparison.
- [ ] Measure in-memory matching/update latency separately from CSV parsing and full replay throughput. Collect per-operation distributions for add, cancel, modify, and crossing match, including p50/p99/p99.9 when sample count supports them, plus events/second. Store sample count, repetitions, variability, memory high-water mark, and allocations after warm-up. State clock and timing-overhead method; batched timing can reduce distortion from per-event clock calls.
- [ ] Profile first, then compare changes one by one: contiguous metadata and node pools, ID-map alternatives, fewer pointer chases and unpredictable branches, preallocation, and avoiding syscalls in the hot path. Re-run correctness and the same workload after each change. If the compiler optimizes away the operation or the benchmark includes input generation/output, fix the harness before reporting a result.
- [ ] Publish only measurements actually made on Ayush's hardware, with context and raw/summary artifacts. No estimated nanosecond claim, no assertion that simulated latency equals exchange end-to-end latency, and no claim that a better mean guarantees a better p99.9.

## 6. Learning notes and sources

- **Before matcher:** bid/ask, spread, tick, market vs limit, passive vs aggressive, partial fill, price-time priority. Hand-calculate a small book.
- **During replay:** L1 top of book vs L2 aggregated depth vs L3 order events; add/cancel/execution; visible vs hidden; queue position is local to the visible modeled book. Trace sample rows by hand before reading parser code.
- **During benchmarks:** CPU cache/locality, allocation, branch misses, throughput vs latency, why p99 matters, and how measurement overhead or thermal/frequency changes distort results.
- **At report/demo:** distinguish a simulated fill from an observed feed event; explain why visible single-venue replay alone does not measure market impact, adverse selection, realistic strategy P&L, or exchange-grade latency.
